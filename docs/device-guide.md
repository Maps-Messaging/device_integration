# Device library: usage and integration guide

This is the entry point for using the device library with MapsMessaging. It documents the **current** Java interfaces, rather than inventing a separate REST service or new device protocol.

- [Every registered device and its special considerations](devices.md)

## What it does

The library manages directly attached **I²C, SPI, 1-Wire, GPIO and serial** hardware. Drivers expose `DeviceController` interfaces for state reads (`getDeviceState()`), optional configuration reads (`getDeviceConfiguration()`), configuration/commands (`updateDeviceConfiguration(byte[])`) and schema metadata (`getSchema()`). Not every controller implements a writable command, and a display or EEPROM is not a telemetry sensor.

The MapsMessaging **server**, not the driver, is responsible for topics and registering/associating schemas. A device's current schema generally describes the exact JSON returned by `getDeviceState()`; some commands or configuration contracts are supplied separately as schema extension metadata. Do not validate an update command against a state schema.

This release uses **JSON** for controller data. A future Protobuf/Avro implementation would require a matching wire-schema and media-type contract; there is no claim that the current `getSchema()` interface directly supplies Protobuf descriptors.

## Get started

1. Set up the bus, kernel interfaces, runtime and non-root permissions as described in [Linux setup](linux-setup.md).
2. Attach devices with correct voltage and address wiring. **Do not connect 5 V signals to 3.3 V-only Pi pins.** Use appropriate level translation or a board designed for 3.3 V I/O.
3. Start the server or create `DeviceBusManager` in a JDK 25 process with Pi4J 4.0.2. The direct device manager builds FFM I²C/SPI/GPIO providers; serial uses jSerialComm; Linux 1-Wire reads the kernel filesystem.
4. For I²C, scan a supported bus or explicitly mount a driver by its registered `deviceName` and numeric address. For SPI, supply `spiBus`, `spiChipSelect`, `spiMode`, `resolution` and `channels`. Linux 1-Wire discovers `28-*` directories with `w1_slave`.
5. Retrieve the controller's **mounted** `getSchema()` for its actual device variant, associate it with the topic before publishing its state, and publish bytes from `getDeviceState()`. Device configuration/command schemas are different from output state schemas.
6. Check an initial sample and device status before trusting measurements; warm-up, calibration, stale samples, and occasional error strings are normal for several sensor families.

## APIs and schemas

| Call | Meaning |
| --- | --- |
| `getName()`, `getDescription()`, `getType()` | Device identity and category |
| `getSchema()` | Current output JSON Schema metadata, with controller-specific configuration/command extensions where supported |
| `getDeviceState()` | Current JSON state bytes; can be `{}` for output-only controllers |
| `getDeviceConfiguration()` | Configuration/status JSON where exposed; not necessarily writable or the same shape as state |
| `updateDeviceConfiguration(byte[])` | Optional write or command operation; check the device reference before sending |
| `close()` | Release controller/hardware resources as supported by the implementation |

### Schema behaviour to know

- **Readings can be unavailable.** Some sensor controllers emit a text error for a failed field; others can omit fields or yield `{}` on a failed poll. Use the mounted controller's current schema, not hand-written field expectations.
- **Timestamp** is generated by the controller as an ISO-8601 string where applicable. Some output devices intentionally have no timestamp.
- **Device state is not configuration.** For example an SPI ADC emits a `current` array while its resolution/channel count is returned as configuration metadata.
- **Displays:** HT16K33 reports last text/brightness/blink/enabled; LCD1602 and ST7735 currently return `{}` from the public state method and accept separate commands.
- **EEPROM:** Its state describes configured model/capacity; arbitrary bytes are accessed only with bounded READ/WRITE commands.
- A schema has a stable controller identity and version as defined by the current implementation. Avoid assuming the same schema for different sensor variants, especially Gravity gas and SEN6x.

## Choosing and validating a device

See [device-specific instructions](devices.md) for addresses, supported features and limitations. Hardware discovery is best effort, and sharing an I²C address does **not** imply two devices can coexist on the same bus. Explicitly identify address-collision devices. The demo PMSA003I/SCD41/TSL2561 drivers simulate values and are excluded from normal physical I²C discovery.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| No I²C device | Bus enabled, correct `/dev/i2c-*` node, address, pull-ups, bus number, non-root permissions |
| Wrong driver at `0x68` | MPU6050 versus DS3231; identity check and actual module wiring |
| Missing or error-valued readings | Sensor warm-up, CRC, calibration, sampling interval and supply voltage |
| SPI channels remain zero | `/dev/spidev*`, chip select, SPI mode, clock, reference voltage and ground |
| 1-Wire missing | Kernel modules, pull-up resistor, `/sys/bus/w1/devices/28-*/w1_slave` |
| LED/LCD command has no visible effect | Device/controller type, expected command JSON, display enable/brightness, bus contention |
| EEPROM beyond 4 KiB inaccessible | Explicit device capacity; safe default is AT24C32/4096 bytes |
| Schema mismatch | Compare the bytes from `getDeviceState()` to the **same mounted instance's** `getSchema()`, not its command schema |

Physical verification remains necessary. Automated fixtures exercise registers and serialization but cannot validate every breakout board, voltage level, bus timing or calibration.
